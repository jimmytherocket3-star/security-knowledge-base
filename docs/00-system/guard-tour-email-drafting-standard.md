# Guard Tour Email Drafting Standard

## 1. Purpose

เอกสารนี้กำหนดมาตรฐานสำหรับ AI ในการตรวจสอบข้อมูลและจัดทำร่างอีเมลสรุปผลการปฏิบัติงาน Guard Tour เพื่อให้รูปแบบรายงานมีความสม่ำเสมอ ถูกต้อง ตรวจสอบย้อนกลับได้ และไม่สร้างข้อมูลที่ไม่มีหลักฐานรองรับ

## 2. Source Priority

ก่อนจัดทำอีเมล ต้องตรวจสอบข้อมูลจากแหล่งต่อไปนี้ตามลำดับ

1. Daily Guard Tour Report ของรอบตรวจนั้น
2. Remark หรือรายละเอียดที่บันทึกอยู่ภายใน Guard Tour Report
3. อีเมลจากฝ่ายอาคารหรือหน่วยงานที่เกี่ยวข้องกับอาคารนั้น
4. อีเมลหรือข้อมูลจาก SOC ที่เกี่ยวข้องกับการเปลี่ยนแปลง Guard Tour
5. ห้ามอนุมานสาเหตุของ Skip หากไม่มีข้อมูลรองรับ

ข้อมูลในอีเมลต้องสามารถย้อนกลับไปยัง Source ได้

## 3. Email Structure

หัวเรื่องให้ใช้รูปแบบเดิมของรายงาน Guard Tour โดยเปลี่ยนชื่ออาคารและวันที่ให้ตรงกับรายงาน

ตัวอย่างรูปแบบ:

`สรุปผลการปฏิบัติงาน Guard Tour อาคาร [ชื่ออาคาร] ประจำวันที่ [วันที่]`

เนื้อหาอีเมลประกอบด้วย

- อาคาร (Location)
- แผนทั้งหมด (Planned)
- ดำเนินการสำเร็จ (Completed)
- ไม่สำเร็จ (Not Completed)
- ยกเลิก (Cancel)
- สถานะปัญหา / ความผิดปกติ
- ผลการตรวจแยกแต่ละรอบ
- รายละเอียด Skip หรือความผิดปกติ ถ้ามี

## 4. Multiple Guard Tour Rounds

กรณีอาคารเดียวมี Guard Tour มากกว่า 1 รอบในวันเดียวกัน ให้รวมอยู่ในอีเมลฉบับเดียว

แต่ต้องแยกข้อมูลของแต่ละรอบให้ชัดเจน เช่น

```text
รอบ 08.00 - 08.39 น.
- Planned: 38 จุด
- Completed: 38 จุด
- Skip: 0 จุด

รอบ 14.00 - 14.35 น.
- Planned: 38 จุด
- Completed: 37 จุด
- Skip: 1 จุด
```

ห้ามรวมตัวเลขของสองรอบจนไม่สามารถตรวจสอบผลแต่ละรอบได้

## 5. Normal Result

หากรอบตรวจไม่มี Skip และไม่พบความผิดปกติ ให้แสดงเฉพาะผลตัวเลขของรอบนั้น

ไม่จำเป็นต้องสร้างรายละเอียดเพิ่มเติมในแต่ละจุดตรวจ

ตัวอย่าง:

```text
รอบ 08.00 - 10.45 น.
- Planned: 66 จุด
- Completed: 66 จุด
- Skip: 0 จุด
```

## 6. Skip Handling

เมื่อพบ Skip ต้องตรวจสอบรายละเอียดของจุดนั้นโดยตรง

อย่างน้อยต้องระบุข้อมูลที่มีอยู่จริง เช่น

- ตำแหน่ง
- ชั้น
- QR Code
- รายการที่ถูก Skip
- รายการตรวจอื่นที่ดำเนินการสำเร็จ
- Remark หรือสาเหตุ ถ้ามี

ตัวอย่าง:

```text
1. ตู้ FHC-001 และลิฟท์ไฟร์แมน ชั้น 4
- QR Code: L1002612
- รายการที่ Skip: การสแกน QR Code
- รายการตรวจอื่นของจุดดังกล่าวดำเนินการแล้ว
```

## 7. Skip Reason Verification

เมื่อพบ Skip ห้ามสรุปสาเหตุทันทีจากสถานะ Skip เพียงอย่างเดียว

ต้องตรวจสอบว่าใน Guard Tour Report มี

- Remark
- Cause
- Note
- ข้อความอธิบายจากเจ้าหน้าที่

หรือไม่

### หากมีสาเหตุ

ให้ใส่สาเหตุตามข้อมูลต้นทาง โดยสามารถปรับภาษาให้กระชับและถูกต้อง แต่ห้ามเปลี่ยนความหมาย

### หากไม่มีสาเหตุ

ต้องระบุให้ชัดว่า

> ไม่พบการระบุสาเหตุของการ Skip ใน Daily Guard Tour Report

ห้ามคาดเดาว่าเกิดจาก

- เจ้าหน้าที่กดผิด
- QR Code เสีย
- พื้นที่ปิด
- ฝ่ายอาคารสั่งยกเลิก
- Event
- งานซ่อมบำรุง

เว้นแต่มี Source ยืนยัน

## 8. Building Email Cross-Check

หาก Guard Tour มี Skip และไม่มีสาเหตุในรายงาน ต้องตรวจสอบอีเมลจากฝ่ายอาคารหรือหน่วยงานที่เกี่ยวข้องเพิ่มเติม

คำค้นที่ควรตรวจสอบ ได้แก่

- ชื่ออาคาร
- Guard Tour
- การ์ดทัวร์
- QR Code
- หมายเลข QR Code
- จุดตรวจ
- Skip
- ยกเลิก
- งด
- ยกเลิกสแกน
- งดสแกน
- ไม่ต้องสแกน

ควรตรวจสอบช่วงวันที่และเวลาที่สัมพันธ์กับ Guard Tour รอบนั้น

## 9. Cancellation Verification

หากพบอีเมลจากฝ่ายอาคารที่ยืนยันว่าให้ยกเลิกหรืองดสแกน Guard Tour ให้ระบุข้อมูลตาม Source เช่น

- ผู้แจ้ง / หน่วยงาน
- วันที่หรือช่วงเวลา
- พื้นที่หรือจุดที่ได้รับผลกระทบ
- เหตุผลที่แจ้ง
- จุดหรือรอบที่งดสแกน

หากไม่พบข้อมูล ให้ระบุว่า

> จากการตรวจสอบอีเมลที่เกี่ยวข้อง ไม่พบอีเมลจากฝ่ายอาคารที่แจ้งยกเลิก งด หรือไม่ต้องสแกน Guard Tour / QR Code สำหรับรอบดังกล่าว

ห้ามสรุปว่า Skip เกิดจากฝ่ายอาคารหากไม่มีหลักฐาน

## 10. Abnormal Equipment Findings

กรณี Guard Tour Completed ครบ แต่พบ Remark เกี่ยวกับอุปกรณ์หรือสภาพพื้นที่ ให้ถือว่าเป็น “ข้อสังเกต / ความผิดปกติ” แยกจาก Skip

ตัวอย่าง:

```text
พบข้อสังเกตเกี่ยวกับอุปกรณ์ จำนวน 7 จุด

1. อุปกรณ์ Pull Down ยังไม่มีสลักคริสตัล จำนวน 5 จุด
2. อุปกรณ์หัวทองเหลืองยังไม่ได้ติดตั้ง จำนวน 2 จุด
```

การ Completed ครบทุกจุดไม่ได้หมายความว่าไม่มีความผิดปกติ

AI ต้องตรวจสอบ Remark เพิ่มเติมเสมอสำหรับรายงานที่มี Remark

## 11. Duplicate Findings Across Rounds

หากความผิดปกติเดียวกันพบทั้งสองรอบ ไม่จำเป็นต้องรายงานเป็นเหตุใหม่สองครั้ง

ให้สรุปเป็นรายการเดียว และระบุว่า

> จากการตรวจทั้ง 2 รอบ พบข้อสังเกตในรายการอุปกรณ์ดังกล่าวในลักษณะเดียวกัน

เว้นแต่สถานะมีการเปลี่ยนแปลงระหว่างรอบ ซึ่งต้องรายงานแยก

## 12. Attachments

อีเมลของแต่ละอาคารต้องแนบ Daily Guard Tour Report ของทุกรอบที่นำมาใช้ในการสรุป

ตัวอย่าง:

`อาคารมี 2 รอบตรวจ → แนบรายงาน 2 ไฟล์ในอีเมลฉบับเดียว`

ไฟล์แนบต้องตรงกับ

- อาคาร
- วันที่
- รอบเวลา

ก่อนสร้าง Draft ต้องตรวจสอบชื่อไฟล์ให้ถูกต้อง

## 13. Recipients

หาก KB หรือคำสั่งปัจจุบันยังไม่ได้กำหนดผู้รับและ CC ให้เว้นช่อง To และ CC ไว้

ห้ามเดารายชื่อผู้รับเองจากอีเมลเก่า เว้นแต่ผู้ใช้สั่งให้ใช้รายชื่อดังกล่าว

## 14. Sender Signature / Contact Information

สำหรับอีเมล Guard Tour ที่ร่างในนามผู้ใช้ ให้ใส่ลายเซ็นและข้อมูลติดต่อกลับดังนี้ เว้นแต่ผู้ใช้จะสั่งให้ใช้ข้อมูลอื่นในงานนั้น

```text
Best Regards,

Sittipong Homjai l สิทธิพงษ์ หอมใจ
SOC Operator - Security Operation Centre (SOC)
Senses Property Management Company Limited

Mobile : 085-112-8002
Mail : sittipong.h@senses.co.th
```

ต้องคงชื่อ ตำแหน่ง บริษัท หมายเลขโทรศัพท์ และอีเมลตามข้อมูลที่อนุมัตินี้ และห้ามเปลี่ยนเป็นข้อมูลจากลายเซ็นของบุคคลอื่นหรืออีเมลต้นแบบ

## 15. Existing Draft Handling

เมื่อผู้ใช้ต้องการสร้าง Draft ใหม่

- ห้ามลบ Draft เดิม
- ห้ามเขียนทับ Draft เดิม เว้นแต่ผู้ใช้สั่งให้แก้ฉบับเดิมโดยตรง
- สร้าง Draft ใหม่สำหรับฉบับที่ปรับปรุง

หากมีหลาย Version ควรรักษาฉบับก่อนหน้าไว้เพื่อให้ผู้ใช้เปรียบเทียบได้

## 16. Writing Style

ใช้รูปแบบอีเมลทางการของ SOC

หลักการเขียน:

- กระชับ
- ตรวจสอบง่าย
- ใช้ศัพท์ Guard Tour / Planned / Completed / Skip ตามระบบ
- ไม่เพิ่มคำอธิบายที่ไม่มี Source
- แยก Facts ออกจากการตีความ
- ความผิดปกติต้องระบุจุดและข้อมูลอ้างอิงเท่าที่มี
- หากไม่พบข้อมูล ให้บอกว่าไม่พบ แทนการคาดเดา

## 17. Final Verification Checklist

ก่อนสร้าง Gmail Draft ต้องตรวจสอบว่า

1. วันที่ถูกต้อง
2. อาคารถูกต้อง
3. จำนวน Routes ถูกต้อง
4. Planned ถูกต้อง
5. Completed ถูกต้อง
6. Skip ถูกต้อง
7. เวลาเริ่มและสิ้นสุดของแต่ละรอบถูกต้อง
8. ตรวจ Remark แล้ว
9. ตรวจสาเหตุ Skip แล้ว
10. หากไม่มีสาเหตุ ได้ตรวจอีเมลฝ่ายอาคารแล้ว
11. ไม่ได้ระบุสาเหตุที่ไม่มี Source
12. ความผิดปกติของอุปกรณ์ถูกสรุปครบ
13. แนบ Guard Tour Report ครบทุกรอบ
14. To / CC เป็นไปตามคำสั่งผู้ใช้
15. ลายเซ็นและข้อมูลติดต่อกลับตรงกับข้อมูลผู้ใช้ที่อนุมัติ
16. ไม่ได้ลบหรือเขียนทับ Draft เก่าโดยไม่ได้รับคำสั่ง

## 18. AI Decision Rule

หลักสำคัญที่สุด:

**Report what is known, verify what can be verified, and explicitly state what is not found. Never invent the reason for a Guard Tour Skip.**

เมื่อ Source ไม่เพียงพอ ให้ใช้ข้อความลักษณะ

> ไม่พบข้อมูลยืนยันสาเหตุจากเอกสารและอีเมลที่ตรวจสอบ

แทนการคาดเดา
